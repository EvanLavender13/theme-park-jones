# Feature: Sim Math

## Summary

sim-math gives the simulation its own exp and log, and guards the two ways the C runtime could still make results differ between builds. simExp and simLog are ports of musl's exp and log, which are Arm's optimized routines, kept under Arm's MIT notice. They are within one ULP of the correctly rounded result, and they return IEEE's values for zeros, infinities, NaN, and arguments past overflow and underflow. They are built into tpj_sim with its flags, so both builds compute them with the same basic operations in the same order. A CMake script lists the undefined symbols of tpj_sim's archive with the toolchain's nm and fails on any C runtime transcendental function. A test runs it on tpj_sim, and another proves it rejects a planted call to exp. In debug builds, constructing a World checks by arithmetic that the thread's floating-point environment is the default: round-to-nearest, with subnormals neither flushed to zero nor read as zero. Printing exp and log outputs in tpj_scenarios, and comparing them across builds, belong to cross-build-check.

## Acceptance criteria

1. For every argument in a checked-in table of correctly rounded reference values, simExp and simLog each return the table's value or a double adjacent to it. The table is generated by a checked-in script at a precision well beyond double, which makes its values correctly rounded. Its arguments cover each function's whole finite domain with random mantissas, so that every region of the argument range is sampled. They also cover the separately handled ranges: arguments near 0 for simExp and near 1 for simLog, subnormal arguments to simLog, and arguments around simExp's overflow threshold and around the thresholds where its result turns subnormal and where it rounds to zero.
2. The special values are exact. simExp returns 1 for +0 and -0, +infinity for +infinity and for any argument of 710 or more, +0 for -infinity and for any argument of -746 or less, and a NaN for a NaN. simLog returns -infinity for +0 and -0, +infinity for +infinity, +0 for 1, and a NaN for any argument below zero, including -infinity, and for a NaN.
3. In a debug build, constructing a World (directly, by copyWorld, or by loadWorld) throws WorldInvariantError on a thread whose rounding direction is not to-nearest, whose results flush to zero, or whose arithmetic reads subnormal operands as zero, and it succeeds in the default environment. Tests that change the environment restore it.
4. The symbol check passes on tpj_sim's archive as built by the preset under test.
5. The symbol check fails on an archive that holds an object calling the C runtime's exp, and its report names exp and the object that references it.

## Medium

This feature introduces no fields or flows. It provides:

- simExp and simLog: believable-guests' softmax and any later simulation code that needs e^x or ln x call these, never std::exp or std::log.
- The symbol check: every later capability's code in tpj_sim passes through it, so a transcendental call from any module fails the tests.
- The environment check: every world a test or the debug app creates runs it.
- The functions' outputs over fixed inputs: tpj_scenarios prints them, and cross-build-check compares them between builds.

## Principle checks

- Principle 10: criteria 1 and 2. The simulation's exp and log are computed by tpj_sim's own code, from correctly rounded basic operations in a fixed order, so a build's C runtime cannot change their results. Criterion 4 shows that tpj_sim calls no C runtime transcendental function, and criterion 5 that the check would catch one. Criterion 3 shows that, in a debug build, no world is created on a thread whose floating-point environment would change its arithmetic. Bit-identity of the outputs across builds is cross-build-check's to prove.

No other principle is at stake: the feature touches no park content, saves, or components.

## Spec changes

src/sim/SPEC.md: replace the final paragraph, beginning "Stepping is deterministic", with:

"Stepping is deterministic: the same world state stepped the same number of times gives the same result, bit for bit, on every supported build (decision 0022). tpj_sim builds with -ffp-contract=off, and simulation code never calls the C runtime's transcendental math functions. It calls simExp and simLog from sim/sim_math.h instead. They are ports of musl's exp and log (musl v1.2.5, Arm's optimized routines), kept under Arm's MIT notice, and built from basic operations whose order and rounding every build shares. Each is within one ULP of the correctly rounded result, and each returns IEEE's special values. simExp gives 1 for zero of either sign, +infinity for +infinity and for arguments of 710 or more, +0 for -infinity and for arguments of -746 or less, and a NaN for a NaN. simLog gives -infinity for zero of either sign, +infinity for +infinity, +0 for 1, and a NaN for a NaN and for any argument below zero.

cmake/check_sim_symbols.cmake enforces the rule, run as cmake -DNM=<the toolchain's nm> -DARCHIVE=<archive> -P cmake/check_sim_symbols.cmake. It lists the archive's undefined symbols with nm -u, and it fails if any is on its denylist, printing a line '<symbol> referenced by <object>' for each such symbol. It also fails if nm fails or an argument is missing. The denylist holds exp, exp2, exp10, expm1, log, log2, log10, log1p, pow, sin, cos, tan, asin, acos, atan, atan2, sinh, cosh, tanh, asinh, acosh, atanh, sincos, cbrt, hypot, erf, erfc, tgamma, lgamma, and lgamma_r, and the complex functions cexp, clog, cpow, csqrt, csin, ccos, ctan, casin, cacos, catan, csinh, ccosh, ctanh, casinh, cacosh, catanh, cabs, and carg. Each name is denied in its f and l forms too, as glibc's __<name>_finite alias, and behind MinGW's __imp_ prefix. Exactly rounded functions such as sqrt, floor, and fmod stay allowed. GCC calls them legitimately, and every runtime gives the same result. A test runs the check on tpj_sim's archive.

The results also depend on the floating-point environment. It must be round-to-nearest, with subnormals neither flushed to zero nor read as zero. In debug builds, constructing a World checks the constructing thread's environment by arithmetic, with no platform-specific code, and throws WorldInvariantError if it is not the default. The environment is per thread, so the check covers the thread that creates the world."

## Dependencies

- registered-walk and text-saves: World, copyWorld, loadWorld, and WorldInvariantError. Merged.
- musl v1.2.5's src/math/exp.c, exp_data.c, log.c, and log_data.c, fetched from git.musl-libc.org when implementing.
- The toolchain's nm, which CMake records as CMAKE_NM on both builds.
- Python 3's decimal module, for generating the reference table.

## Out of scope

- Printing exp and log outputs in tpj_scenarios, and comparing them across builds: cross-build-check.
- pow, trigonometry, and other functions: the capability's further-simulation-math candidate, gated on a feature that needs one.
- Checking the floating-point environment in release builds, or at every tick rather than at world creation.
- Floating-point exception flags and errno, which the simulation never reads.

## Open questions

- Whether the environment check should also run at each stepWorld, since a library loaded after a world is created could change the environment. Resolved if a divergence is ever traced to one.
