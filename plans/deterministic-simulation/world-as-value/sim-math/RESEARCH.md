# Research: sim-math

## What does porting musl's exp and log change, and what does this build make of it?

The four source files, exp.c, exp_data.c, log.c, and log_data.c, are identical at musl's v1.2.5 tag and on master, so the port can pin v1.2.5. Each file carries the notice "Copyright (c) 2018, Arm Limited" with an MIT SPDX line. musl's COPYRIGHT file names Arm among the math library's copyright holders and gives the standard MIT permission text, which a port must reproduce beside the copyright line.

exp handles its edge cases before the main path. Arguments whose magnitude is below 2^-54 return 1 + x, which is 1 for every such finite x. Infinity returns infinity, negative infinity returns +0, NaN returns a NaN, arguments of magnitude 1024 or more otherwise overflow to +infinity or underflow to +0, and arguments of magnitude between 512 and 1024 take a special case that scales in two steps and rounds once more near the subnormal range, so subnormal results keep the same error bound. The main path rounds x·128/ln2 to an integer k by adding and subtracting 1.5·2^52, which is exact in round-to-nearest, looks up 2^(k/128) as a table value plus a tail, and evaluates a degree-5 polynomial for exp(r).

log handles arguments within about 1/16 of 1 by a separate polynomial of degree 11 with a split of r into high and low halves, and returns exactly +0 for 1. Zero of either sign returns negative infinity, positive infinity returns itself, negative arguments and NaN return a NaN, and subnormal arguments are scaled by 2^52 and their exponent corrected. The main path splits x into 2^k·z, picks one of 128 subintervals from z's top mantissa bits, and without fused multiply-add computes r from a second table of c's high and low parts. That second table, tab2, exists only for the non-FMA path, which is the one this build takes.

The macro helpers map one to one. asuint64 and asdouble become std::bit_cast. eval_as_double and predict_false become nothing. __math_oflow(0), __math_uflow(0), __math_divzero(1), and __math_invalid(x) become +infinity, +0, negative infinity, and a NaN. fp_force_eval and fp_barrier exist only to raise the underflow flag and are dropped. WANT_ROUNDING is 1 in musl's default build; kept at 1, its two branches (exp's 1 + x for tiny x, and exp's and log's guards against -0 in downward rounding) change no result in round-to-nearest, so the port may keep or drop them without changing a bit. exp_data.c also holds exp2's shift and polynomial, which exp does not read and the port drops.

Every signed and unsigned step is defined in C++20: the unsigned subtractions that wrap on purpose, and log's arithmetic right shift of a negative int64_t, which C++20 defines. The expression orders matter for bit identity, and with -ffp-contract=off and no fast-math GCC keeps them, at -O0 and -O2 alike. The clang-tidy friction to expect is readability-implicit-bool-conversion on bit tests, misc-const-correctness on locals, and readability-isolate-declaration on musl's grouped declarations. readability-magic-numbers is off in this project, so the coefficients can stay as hex literals.

Arm states the error as about 0.51 ULP for exp and 0.52 for log, so a result is the correctly rounded value or one of its two neighbors. A transcription error in a table entry large enough to matter moves the result further than a neighbor for inputs in that entry's subinterval. One too small to do so leaves a function that is still within a ULP and still bit-identical across builds, which is all the simulation needs.

Rejected: keeping musl's C and compiling it as C, since tpj_sim is a C++ target with its own warnings and clang-tidy, and the helpers are the only C-specific part. Reproducing musl's outputs bit for bit in a test, since the reference would need a second transcription of the same tables, and cross-build identity is cross-build-check's to prove.

Sources: https://git.musl-libc.org/cgit/musl/tree/src/math/exp.c?h=v1.2.5 — exp's paths and helpers; https://git.musl-libc.org/cgit/musl/tree/src/math/log.c?h=v1.2.5 — log's paths and the non-FMA branch; https://git.musl-libc.org/cgit/musl/tree/src/math/exp_data.c?h=v1.2.5 and https://git.musl-libc.org/cgit/musl/tree/src/math/log_data.c?h=v1.2.5 — the tables; https://git.musl-libc.org/cgit/musl/tree/COPYRIGHT — the MIT text and Arm's attribution.

## How can correctly rounded reference values be generated with only the Python standard library?

The decimal module's exp and ln are documented as correctly rounded in the context's precision, Decimal(float) converts a double exactly, and float(Decimal) rounds correctly to the nearest double, including into the subnormal range. Computing at 60 significant digits and then rounding to a double rounds twice, which could only go wrong if the true value lay within about 10^-60 of the midpoint between two doubles. Lefèvre and Muller's exhaustive search found that about 120 bits always suffice to round exp and log correctly in double precision, and 60 digits are nearly 200 bits, so the result is the correctly rounded double. The decimal context's default exponent range covers exp's whole domain. Writing each input and expected value as a hexadecimal float literal, from float.hex, makes the C++ table exact. mpmath is not installed here, and decimal needs nothing.

Coverage matters more than count. Random arguments with uniformly distributed mantissas land in every one of each routine's 128 subintervals: with a few thousand samples per function, missing any one is vanishingly unlikely. Arguments near 0 for exp, near 1 for log, in the subnormal range for log, and around exp's overflow threshold (about 709.78) and underflow thresholds (results turning subnormal below about -708.4, and rounding to zero below about -745.13) reach the separate paths.

Rejected: mpmath or MPFR, since they add a dependency for what decimal already does exactly. Comparing against glibc's exp and log, since they are the same Arm algorithms but glibc picks an FMA variant on CPUs that have it, so they are not a reference and not stable across machines.

Sources: https://docs.python.org/3/library/decimal.html — exp and ln are correctly rounded, and conversion from float is exact; https://researchr.org/publication/LefevreM01 — Lefèvre and Muller, "Worst Cases for Correct Rounding of the Elementary Functions in Double Precision", ARITH 15, the precision correct rounding needs.

## How can a world check that the floating-point environment is the default, portably?

Two settings change what tpj_sim's arithmetic returns on x86-64: the rounding direction, and the flush-to-zero and denormals-are-zero bits in the SSE control register. Code built with -ffast-math, or a library loaded with its startup object, sets the latter. std::fegetround reports only the rounding direction. It says nothing of the flush bits, and mingw-w64 implements it through its own control-word wrapper rather than reading the SSE register directly. Reading the register itself needs an x86 intrinsic, which would be tpj_sim's first platform-specific code.

A probe that does arithmetic measures exactly what the simulation relies on, with no platform code. Adding 1.5·2^-53 to 1 rounds up to the next double in round-to-nearest and upward, and adding -1.5·2^-53 to -1 rounds away from zero in round-to-nearest and downward, so only round-to-nearest rounds both away from 1. Halving the smallest normal double gives a nonzero subnormal unless flush-to-zero is set, and doubling the smallest subnormal gives twice it unless denormals-are-zero is set. The operands must be read through volatile, or GCC folds the operations at compile time under the default rounding assumption. The environment is per thread, so a probe checks the thread that runs it.

Rejected: std::fegetround alone, since it misses the flush bits. _mm_getcsr, since it is x86-specific. Setting the environment at world creation instead of checking it, since it would hide whatever changed it.

Sources: https://en.cppreference.com/w/cpp/numeric/fenv/feround — fegetround covers the rounding direction only; https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html — -ffast-math links a startup object that sets flush-to-zero; https://github.com/mingw-w64/mingw-w64/blob/master/mingw-w64-crt/misc/fegetround.c — mingw-w64's fegetround.

## How does the symbol check run from ctest on both builds, and how is it proven?

tpj_sim's archive currently has no undefined math symbols at all: nm -u lists only C++ runtime, sanitizer, and string functions. A CMake script run with cmake -P can call the toolchain's own nm, which CMake records as CMAKE_NM on both the Linux and MinGW builds, parse its per-object listing, and fail with message(FATAL_ERROR) naming each denied symbol and the object that references it. That needs no shell, Python, or grep on Windows, so the same test runs on every preset. MinGW may reference an imported function through an __imp_ symbol, so a name is denied with or without that prefix.

The planted violation is a separate static library, built from one source file that returns std::exp of a parameter, so GCC cannot fold the call. Running the check on it must fail and name exp. ctest's PASS_REGULAR_EXPRESSION on the check's report makes the test pass only when the check rejected the symbol for the right reason, where WILL_FAIL would also pass on an error in the script itself.

Rejected: a bash or Python script, since neither is guaranteed on the Windows build's PATH. A post-build step on tpj_sim, since the milestone asks for a test, and pre-push runs the tests. Checking the linked executables, since they legitimately link the C runtime's math through rendering code.

Sources: https://cmake.org/cmake/help/latest/variable/CMAKE_NM.html — the toolchain's nm; https://cmake.org/cmake/help/latest/prop_test/PASS_REGULAR_EXPRESSION.html — output-based pass criteria; https://sourceware.org/binutils/docs/binutils/nm.html — the -u listing.
