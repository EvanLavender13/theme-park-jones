# Research: Following Footfall

## How is a decaying metric kept so a tick's work follows the movers?

The standard technique holds each place's value together with the time it last changed, and applies the decay owed since then only when the value is read or next changed. A place nobody touches costs nothing until someone asks about it. Streaming systems call this forward decay: rather than recomputing every item's weight as time passes, each item's weight is fixed when it arrives, and the elapsed time is applied once at query time. Exponential decay fits this exactly, because decaying for a ticks and then for b ticks equals decaying for a plus b ticks, so the decay owed over any idle gap is one factor raised to the length of the gap. Rate counters in networking and memory heatmaps use the same idea, a value plus a timestamp, updated only on access.

For this repository, the factor raised to a gap's length must be computed the same way on every build (decision 0022). tpj_sim already has simExp and simLog, ports of musl's routines built from basic operations, so a decay of k ticks can be simExp(k times simLog of the per-tick factor), or the factor raised to k by repeated squaring, which uses only multiplication. Either gives the same bits on every build. Neither gives the same bits as applying today's rule once per tick, V plus (0 minus V) divided by 300, k times over, because rounding accumulates differently. Decision 0031 allows this: the metric's spec states the rule it uses instead. A stretch that has guests on it every tick can keep today's per-tick rule exactly, so the values differ only after a stretch has sat empty, and then only in their last bits.

Rejected: replaying each idle tick when the value is read, which matches today's bits exactly — a stretch idle for an hour of play owes about 100,000 steps, and a read in a frame or a guest's return would pay them all. Pruning values that have decayed below a small threshold — it changes what the field holds, and is unnecessary when idle values cost nothing per tick.

Sources: https://dblp.uni-trier.de/rec/conf/icde/CormodeSSX09.html — forward decay (Cormode, Shkapenyuk, Srivastava, Xu, ICDE 2009): weights fixed on arrival, decay applied at query time, exponential decay as the practical case; https://qratorlabs.medium.com/rate-detector-21d12567d0b5 — a rate counter kept as a value and a timestamp, decayed on update.

## What must the field medium change to hold such values?

Today's medium has two layers per field (src/sim/medium/SPEC.md). Resolved entries are published by resolvers when intent changes. Stepped entries are published by systems, and each tick's swap replaces the readable stepped entries with those published during that tick, so a source that stops publishing loses its entries. A value that persists therefore has to be republished in full every tick. That is what makes hungry footfall's tick grow with the guest network: stepFootfall rebuilds and republishes one entry per stretch and one per node every tick, and the slot's order by place is rebuilt on its first sample after each swap.

Nothing in the simulation reads hungry footfall. Its one reader is legible's shopContext, which gives a shop ghost's tooltip the committed world's footfall where the ghost would connect. So its values can change in their last bits without changing anything a guest or shop does, but its saved form is state, so saves and world hashes change with it.

Following movers needs a third kind of entry: one a system changes at a single place, which stays readable until it is changed again, carries the tick it last changed, and is read through its owner's rule given the tick of the read. Writes made during a tick must not be seen by other systems in the same tick, as stepped entries are not, so that the order systems run in cannot change results. That means changes are held aside during the tick and applied at its swap, and the swap then costs what the tick changed, not what the field holds. Footfall's value at a node, today the mean of the stretches meeting it published as its own entry, would instead be worked out when read from those stretches, which costs the node's number of stretches.

Rejected: footfall leaving the medium and becoming a guests-module query that legible calls — it would take footfall out of the shared medium that principle 3 and decision 0005 route interactions through, and decision 0031 expects every later metric, such as litter or crowding, to be kept this way, so the medium is where the mechanism belongs. Republishing only the stretches that changed into the stepped layer — the swap drops every entry not republished, so untouched stretches would vanish.

Sources: src/sim/medium/SPEC.md and src/sim/medium/field.h — the layer rule and the swap; src/sim/guests/SPEC.md and src/sim/guests/footfall.cpp — hungry footfall's rule and its per-stretch, per-node republishing; src/legible/preview.cpp — footfall's one reader; src/sim/SPEC.md — simExp, simLog, and the cross-build math rule.
