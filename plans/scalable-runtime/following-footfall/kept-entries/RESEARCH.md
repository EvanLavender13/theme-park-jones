# Research: Kept Entries

## How should the medium hold entries that persist until changed?

The milestone's research settles the technique: hold each value with the tick it last changed and let the owner's rule decay it when read (../RESEARCH.md). What remains is how the medium holds such entries beside the layers it has. src/sim/medium/field.h gives every field a resolved layer and a stepped layer, chooses between them per source by the layer rule, and finds a slot's entries through an order by place that, today, nothing changes in place. Its sampling helpers, positionsAt, positionsInside, and positionsAtAny, already find entries at a place, inside an edge, and at a node's stop places by binary search over that order, and depend on a slot only through its Entries, each with a place, and its ByPlace order.

A kept field registered by its own call, with only kept entries, leaves every existing field's registrations and saves untouched and needs no new layer rule, since a kept field's sources have no other layer to choose. Keeping a kept source's entries in the order their places were first kept, with an order by place beside them like other slots', lets the existing helpers serve both kinds of slot once they take any slot type. The swap then changes a held place's value in place, which leaves the order valid because places never change, and inserts a new place's position into the order, the one step that moves memory, taken only the first time a mover reaches a place. A loaded or copied world rebuilds or carries the order as other slots do, so a hand-edited save in any order still reads correctly.

Holding changes until the swap, rather than writing them at once, keeps the stepped layer's guarantee that no system reads a change made in the same tick, so registration order cannot change results (principle 10). The pending list grows with the tick's changes only.

A field read at a node by its owner's rule, as footfall's node mean needs, needs the edges meeting the node. The network has no such query: stopPlaces gives a node's stop places, and edges() is ordered by carrier and distance. The network's constructor already builds each node's stop places in one pass, and the same pass over the edges can build each node's edge ends, so a node read costs its own number of ends.

Rejected: a fourth layer on every field, chosen by an extended layer rule — it adds a component to every field's schema and save, which the operations registration test and the remade parks' evidence both rule out (the milestone review's finding). Holding a kept source's entries sorted by place with no separate order — a hand-converted or malformed save would silently break the binary searches, where a derived order is rebuilt correctly from any entries. Finding a node's edges at read time by binary search from its stop places — it works, but duplicates the network's own knowledge of its edges in the medium's sampling code, and the constructor already walks every edge. Kept fields of any entry type — every accumulating metric decision 0031 names is a number, and a scalar-only kept field keeps readKept's signature simple.
