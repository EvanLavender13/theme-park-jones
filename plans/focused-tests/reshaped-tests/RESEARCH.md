## What is left to reshape?

plans/focused-tests/RESEARCH.md lists 203 test cases as rewrite, in 53 files, and every one still exists under the name it gives. By module: the sim root 42 (sim_math 9, schema 7, world_checks 7, cycle 6, save 5, fp_environment 4, draw 2, walk 2), sim/medium 19, sim/park 15, sim/routes 7, sim/guests 23, sim/operations 10, legible 19, render 45 (park_mesh 17, ghost_mesh 10, food_overlay 7, picking 7, guest_mesh 4), tools 9, app 13, and one integration test, food_loop_test's. Two entries carry work the shared world checks left behind. edit_sequences_test's randomized test still asserts copy and save, which the shared world checks now prove; its rewrite keeps only validity under commands. stepped_field_test's publication-order test merges into field_test's, which covers both layers.

## Which spec statements are trimmed?

A read of each module's SPEC.md found about 126 statements that fix a layout, a formula, a tuning value, or exact display text as contract: render 27, sim/guests 18, app 14, sim/park 12, sim/routes 12, legible 11, sim/medium 9, sim/operations 9, the sim root 8, tools 6, and views none. bench's and scenarios' specs were not surveyed: their modules are test utilities (rule 6), so no test pins what they say. Most are tuning constants (the guests' weights and rates, render's sizes and lifts, operations' delays), formulas copied from the code (interpolations, projections, Catmull-Rom, the hash's folding), vertex and triangle orders in render, and display text in app and legible.

A few stay because something outside the module depends on the exact detail. In code: app's frame-times line, which bench's report parses; the `tick <t> hash <h>` line, which must match tpj_scenarios's; park's box corner order, which routes and render index; render's windowPoint convention, which app's graph view relies on; and render's uniform set numbers, which SDL_GPU fixes. On disk: the save format and the derived keys saves hold, such as fieldKey and connectorKey, which parks/, tests/parks/, and players' saves depend on. A constant other modules use by name, such as WALK_SPEED, OVERLAY_BAND, SIM_TICK_SECONDS, or the path widths, keeps its name in the spec, but its number is free.

Trimming a statement often uncovers the property it stood in for, which the spec then states: a tool's finish reach exceeds the park's minimum point spacing, so a finished path keeps every point; routes' connection reach exceeds half of every path width. Two such couplings are in code by value only, app's own copy of the park size and render's overlay full scale written as 0.5 rather than read from the meal's relief; they are defects in src/, outside this milestone, and are filed in sound-architecture's deepening candidates.

## What do the repository checks keep?

Four checks in cmake/ gate the tree. Each keeps a run on what it gates, which shows it passes on the real tree, and one planted violation, which shows it can fail; every other case tests the check's own parsing and reporting, case by case, which rule 4 forbids and the capability's criterion drops. The private header check has its run and 17 cases, of which "rejects a planted violation" stays. The layer check has its run and 24 cases; "reports includes of a sibling in the same layer or of a higher layer" is the violation to keep, and "cmake/layers.txt declares the layers of the code, lowest first" pins the table's content, a change-detector of rule 1. The placement check's run is the pre-commit hook on each PLAN.md a commit adds, so ctest keeps only one planted violation, a plan without the section, of its 11 cases. The sim symbol check already has its runs on tpj_sim and tpj_scenarios_lib and its planted call to exp beside tpj_sim's tests, and is unchanged. The cases' scripts in tests/checks/ shrink to the planted trees the kept cases use.

## How should the work be split into features?

By module, bottom-up through cmake/layers.txt, each feature trimming its module's SPEC.md and rewriting its module's inventory entries together, with the repository checks as one feature of their own. A spec trim and the rewrite of the tests that pinned the trimmed detail belong in one change: trimmed first, a spec leaves tests asserting what it no longer says; rewritten first, a test has no spec to derive its property from. Bottom-up order means a rewrite that leaves a property to a lower module finds that module's tests already in their final shape. Small neighbouring modules share a feature, so each feature holds roughly 20 to 45 entries, one test-writer dispatch.

The test-writer's rewrite mode takes findings naming cases and the property each should assert, which an inventory entry is. Its wording names closing-audit findings only, and implementing-features' test pass dispatches only from FEATURE.md's criteria, so the first feature widens both to the inventory's entries. Three entries asked for randomized tests of deterministic rules, which rule 4 forbids; they now ask for a few inputs chosen for a reason.

Rejected: one feature per kind of work, trimming every spec in one and rewriting every test in another — the trim would leave every module's tests out of step with its spec until the second lands, and each is too large for one dispatch. Splitting by the rule each case breaks, change-detectors in one feature and enumerations in another — it touches each test file several times, and many entries break both. One feature per test file — over fifty features for what is mostly one dispatch each.
