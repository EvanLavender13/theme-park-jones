# Research: flow-ledger

## How should stocks and packets be held so that ledger operations commute?

OpenTTD's cargo packets carry a count, their source, the station they first loaded at, their next hop, and their time in transit, and two packets merge only when every attribute that matters is equal. A merged packet is just a larger count of interchangeable units. A stock that holds a count per endpoint and handle is the same idea: units with the same owner and the same address are interchangeable, so they are held as one number, and units with different handles never merge. Packets in transit keep their own arrival time, so nothing about the network after sending can change when they arrive, and they need no merging for anything the slice does.

Replicated data types give the rule for order independence. Operations commute when they are increments of counters, or insertions into a set ordered by content, or when they touch disjoint state. A withdrawal that checks the balance first does not commute with another withdrawal from the same balance: when the stock runs short, which one fails depends on order. So the ledger's writes while stepping are confined to the acting endpoint's own stock. Creation and consumption counts are sums, sent packets go into a list ordered by their contents, and a withdrawal touches only the stock of the entity that makes it. Two producers acting for different entities then give the same ledger in either order. Delivery, which writes other endpoints' stocks, happens only in the swap, where one function does it in a fixed order.

What this suggests: one state component per flow kind on a derived-key entity, as each field has, holding packets ordered by content, stocks ordered by endpoint and handle with zero counts dropped, the created count, and consumed counts per cause. Create, send, and consume take the acting endpoint and change only its stock. The swap delivers due packets, returns undeliverable ones, and settles removed endpoints' stocks.

Rejected: letting a system withdraw from another endpoint's stock — the result would depend on producer order when the stock runs short. Clamping a withdrawal to what the stock holds — it hides a caller's mistake, and the outcome still depends on order. Merging identical packets in transit — nothing needs it, and it is the milestone's packet split and merge deepening candidate. Registering kinds by runtime name in one shared component — a type per kind, like a field's definition, gives each kind its own component, its own name check at registration, and no lookup by string while stepping. Storing causes as strings — the walk has no string field type, so a cause is held as the hashName of its name, the idiom purposes already use.

Sources: https://github.com/OpenTTD/OpenTTD/blob/master/src/cargopacket.h — packet attributes and when packets merge; https://arxiv.org/pdf/1705.09704 — game state is not a commutative replicated type, so commuting must be designed for; https://gafferongames.com/post/deterministic_lockstep/ — any order dependence desyncs a deterministic simulation.
