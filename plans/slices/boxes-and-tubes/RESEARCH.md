# Research: boxes-and-tubes

## How should integration tests be structured so that each slice extends them without adding a file or test per property?

Integration tests that try to show correctness grow with the product of the branches they cross, not the sum: a few layers with a few branches each already give tens of thousands of paths, so such tests settle on covering a sliver and still multiply with every feature (Rainsberger). The unit tests already establish each module's properties against synthetic input, so an integration test earns its place only by checking what no single module can: that the modules together keep a law, or that a consequence crosses them end to end.

Projects with deterministic simulations keep their integration suites from growing with code by making them data-driven. OpenRCT2's replay tests are one parameterized test over every recorded replay file: each replays its commands and fails when the state checksum differs, and a new regression test is a new file with no code. Factorio's integration tests build a small map, place a few objects, run updates, and assert expected conditions, and every test also checks its state CRC against stored values, so determinism is tested by every test rather than by tests of its own. Factorio's suite reached 800 such tests, one per behavior, which is the per-behavior growth this question asks to avoid; its CRC check is the part that scales. This repository already works the data-driven way in one place: scripts/cross-build-check.sh runs every park file in tests/parks/ on both builds and compares their hashes, so a new park is covered without editing the script.

Invariants checked over every run are the scalable kind of assertion: conservation, symmetry, and monotonicity hold for any input, so one assertion covers every park instead of naming expected values (metamorphic testing, which simulation verification uses for exactly this oracle problem). For this game the invariants that span capabilities are that every flow is conserved per cause across its producer and consumer, that a save loads back to an equal world with every module's state registered, and that a run is deterministic with all systems interacting. Run over every file in tests/parks/, they grow with parks, not code; a new flow type adds one entry to a list, since flows are compile-time types.

What remains is behavior a slice promises that is not a law: fed.park feeds its guests, cutting the supply route starves the shop and its guests. These are scenario assertions and cannot be made generic. The research suggests keeping them few and tied one to one to slice criteria, in one place, rather than one file per property.

Golden hashes over time, as OpenRCT2 and Factorio use, catch any change in outcome. They measure what is unchanged rather than what is correct, so every tuning change to the simulation's rules fails them until the golden values are regenerated; tpj_scenarios --slice-parks already regenerates the slice's parks for the same reason.

Stateful property-based testing (RapidCheck's state module) generates random command sequences, here edits to a park, checks invariants after each, and shrinks a failure to a minimal sequence. It finds bugs that appear only after a chain of edits, which neither park files nor scenarios reach.

Rejected: one integration test per slice criterion or per Medium entry — it restates module tests and multiplies files with every slice, as the closing of this slice showed. Golden outcome hashes per park over time — every rule change breaks them, and the cross-build check already compares hashes where they must agree. Stateful property-based testing now — it adds a dependency and a generator for every edit kind; it is a candidate once invariants over park files exist and edit sequences are a known source of bugs.
